# Task: Implement a Codex integration window inside the Unity Editor

Implement a production-ready Unity Editor tool that lets me submit questions and coding tasks to the locally installed OpenAI Codex CLI without leaving Unity.

Use C# and Unity Editor APIs. Inspect the existing project conventions, assembly definitions, namespaces, and Unity version before implementing. Follow existing naming/style conventions. Place Editor-only code in an appropriate Editor folder and assembly; never introduce UnityEditor dependencies into runtime assemblies. Prefer a small, maintainable implementation without unnecessary abstractions or external packages.

## 1. Editor window

Create an EditorWindow named **Codex Tasks**, accessible from **Tools > Codex Tasks**.

Show:
- Codex status: **Shutdown**, **Running (idle)**, or **Working**.
- An editable multiline **Question** text area.
- A read-only, selectable multiline **Answer / Result** text area.
- A reorderable or standard editable list of UnityEngine.Object references, with drag-and-drop support (scene objects and project assets).
- **Start Codex**, **Answer Question**, and **Run Task** buttons, enabled according to state.
- Clear errors and basic progress/log information, including exit codes and relevant stderr when a command fails.

The window must remain responsive throughout execution. Prevent concurrent submissions; disable submission controls while a task is running. Restore sensible state after domain reloads, recompilation, or closing/reopening the window.

## 2. CLI integration and process lifecycle

The integration must work on Windows with an installed `codex.exe` accessible through PATH; allow a configurable absolute executable path as a fallback. Validate the executable and provide a useful error if it is missing or authentication is required.

Do **not** attempt to simulate typing into the interactive Codex terminal or pipe arbitrary commands to a TUI. Use Codex's supported non-interactive execution interface (`codex exec`) or a documented supported persistent API if one is available in the installed version.

Separate *logical session state* from *OS process state*:
- **Shutdown**: integration has not been initialized, or was explicitly stopped.
- **Running (idle)**: initialized and ready for submissions, without an active command.
- **Working**: a Codex command is executing.

If using one `codex exec` subprocess per request, **Start Codex** initializes and validates the integration; it does not need to leave an unused process alive. If a supported persistent Codex session API is chosen instead, manage its lifecycle safely and reconnect when appropriate. Be explicit in code about which approach is used.

Start subprocesses with the Unity project root as working directory. Use argument-safe process invocation and correctly quote/escape paths containing spaces. Capture output and errors without deadlocking, asynchronously wait for completion, and dispose process handles. Do not block Unity's main thread. Return Editor UI changes to the main thread via a safe mechanism (for example, EditorApplication.update). Never run multiple tasks at once. Clean up safely on window disposal/editor exit and provide a way to cancel an active task if feasible.

Do not silently bypass Codex sandboxing or approval policies. Use read-only permissions for Quick Answer operations and project-writing permissions for explicitly requested tasks, following supported CLI flags for the installed version. If some invocation options are version-dependent, check `codex exec --help` and adapt accordingly.

## 3. Initialization (Start Codex)

When Start Codex is pressed:
1. Ensure `Assets/Codex Tasks/` exists (create it if needed).
2. Ensure a project-root `AGENTS.md` contains the workflow rules in section 6 below. If it already exists, preserve its original contents and append/update only a clearly delimited **Unity Codex Tasks Workflow** section. Do not replace the entire file or duplicate the section every time.
3. If the Unity project is inside a Git repository, ensure the **repository-root** `.gitignore` has an appropriate rule that ignores this project's `Assets/Codex Tasks/` directory. Resolve the path relative to the repository root (which may not be the Unity project root). Preserve existing rules and avoid duplicates. Do not create an unrelated `.gitignore` outside the repository. Note that files already tracked by Git cannot be untracked solely by adding an ignore rule.
4. Validate Codex availability, then mark the integration **Running (idle)**.

Files generated under `Assets/Codex Tasks/` are temporary artifacts; do not intentionally include them in version control. Avoid unnecessary AssetDatabase refresh calls, but ensure Unity notices generated text files when necessary.

## 4. Answer Question (`[QuickAnswer]`)

When **Answer Question** is pressed:
1. Read the Question text and validate that it is not blank.
2. Resolve the current object references to clear project-relative asset paths and/or scene object descriptions. For assets, use `AssetDatabase.GetAssetPath`; for scene objects/components, identify the scene path and a stable hierarchy path, and explain when a reference is unsaved or cannot be reliably resolved. Do not assume every UnityEngine.Object is a project asset.
3. Construct a prompt starting with `[QuickAnswer]`, followed by the question and an explicit **Referenced Unity objects** section. Include all valid references. Tell Codex that these references are contextual inputs, not permission to edit them.
4. Execute Codex asynchronously in a mode that does not permit edits to project files.
5. Obtain the final answer from the command's output and have the **Unity Editor integration** write it to `Assets/Codex Tasks/QuickAnswer.txt`. This avoids granting the Codex agent write access just to create the answer file.
6. Populate the Answer / Result text area with that file's contents when execution completes.
7. Keep the window responsive and show failures instead of treating a failed command as a successful answer.

**Strict rule:** Quick Answer must not modify project source files, scenes, prefabs, assets, settings, or other project content. The only intended write is the editor-side update of `QuickAnswer.txt` (plus initialization-time setup if the user explicitly pressed Start Codex). The agent should return its answer as text; the integration saves that text.

## 5. Run Task (`[TaskFile]`)

When **Run Task** is pressed:
1. Validate the question and collect Unity object references as described above.
2. Construct a prompt beginning with `[TaskFile]`, followed by the task request and a **Referenced Unity objects** section.
3. Tell Codex to follow the project-root `AGENTS.md` workflow, implement the requested changes in the Unity project, and produce a concise completion report.
4. Generate a brief descriptive title for the task, or ask Codex to propose one. Sanitize the title for Windows filenames and limit its length.
5. Create a unique report path under `Assets/Codex Tasks/` with format:
   `Task MMDD-XXX {Title}.txt`
   where MM = month, DD = day, and XXX = an incrementing, zero-padded three-digit sequence for that date (001, 002, ...). Use the local date. Determine the next number from existing report files and avoid collisions. `>` must NOT be used because it is illegal in Windows filenames.
6. Pass the exact report path to Codex. The agent should perform the task and write or supply a report containing:
   - Task title and summary
   - Changes implemented
   - Relevant notes, tests, and known limitations
   - **Modified assets / files**, as an explicit list of project-relative paths (including added and deleted files when applicable)
7. Preferably have the integration write the final report from Codex's output, using the known path, rather than depending on the agent to choose its own filename. If feasible, calculate changed paths from a safe before/after project snapshot or version-control diff, while distinguishing pre-existing user modifications; never claim the list is exact unless verified.
8. Show the report in the Answer / Result area after completion. The agent does not need to provide a lengthy terminal response apart from the material needed for the report.

Tasks may modify project files only within Codex's configured sandbox and approval permissions. Preserve unrelated user changes. Do not automatically commit changes.

## 6. `AGENTS.md` workflow section

Add or update the following rules in a clearly delimited section of the project-root `AGENTS.md`:

### Unity Codex Tasks Workflow

- This is a Unity project. Respect its Unity version, assembly definitions, namespaces, project structure, and existing coding style.
- Prompts starting with `[QuickAnswer]` are **read-only questions**. Inspect the codebase and referenced Unity objects as needed, but do not modify, create, rename, or delete any project files. Return a focused plain-text answer. The Unity Editor integration handles writing `Assets/Codex Tasks/QuickAnswer.txt`.
- Prompts starting with `[TaskFile]` are **implementation tasks**. Make the requested changes in the project, without unrelated refactors. Follow the user's exact requirements and preserve existing work. Produce a compact text completion report using the specified report path or the format requested by the Editor integration.
- Task reports must include a short summary, work completed, validation/test results if any, limitations, and a final section titled `Modified assets / files:` listing every known created, modified, or deleted path relative to the Unity project root. State clearly when a change list cannot be verified.
- The `Referenced Unity objects` section in prompts provides contextual targets. Resolve paths carefully. Scene-object references may require reading the scene hierarchy or YAML and may be unavailable if the scene has unsaved changes.
- Never assume a task succeeded without checking process/tool results. Do not invent test results.
- Treat `Assets/Codex Tasks/` as temporary output, not as source code to edit unless the workflow specifically requires a report.

### End Unity Codex Tasks Workflow

The integration must update only this delimited section if it needs to evolve the workflow later.

## 7. UX and robustness

- Preserve the Question text and object-reference list while the window is open and, if reasonable, across Unity domain reloads.
- Show subprocess state changes promptly. Provide a scrollable output area for long reports.
- Expose a Stop/Cancel action while Working if cancellation can be safely implemented; cancel the entire subprocess and return to idle.
- Avoid duplicate Git ignore rules and duplicate AGENTS.md sections.
- Gracefully handle deleted/missing referenced objects, invalid paths, empty responses, Codex errors, unexpected process exits, and access-denied errors.
- Do not hardcode developer-specific usernames or machine paths.
- Avoid disrupting Unity's asset import or compiling cycle when writing reports.
